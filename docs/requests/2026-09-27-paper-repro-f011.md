## Blocker — F-011: `run_pipeline` cannot receive a whole-number float

**What happens.** A step annotated `x_km: float` cannot be run through `run_pipeline` with
`x_km = 2.0`. The MCP **client** serialises 2.0 as the JSON integer `2`, before SmartMDAO sees
it. The strict rule "int does not satisfy float" (cookbook pitfall 5) then rejects it:

```
run_pipeline(float_probe.py, inputs={"x_km": 2})   -> TypeMismatchError: Input 'x_km'=2 (int) ... float
run_pipeline(float_probe.py, inputs={"x_km": 2.5}) -> ok, y_km = 5.0
```

**Why it blocks.** The baseline inputs are full of whole-number floats: altitudes of 550 and 575
km, R_E = 6378 km, 10 W, 26 GHz, μ = 3.98e14. So **no smoke run of the real contract can be made
through the MCP**, and unit costs had to be measured by hand instead. The R3 cost note depends on
those smoke runs.

**Why it will not be the last time.** JSON gives no reliable way to keep 2.0 apart from 2, and
tool calls are written as JSON. Any pipeline with round-number inputs hits this at the MCP
boundary, even though the same values work in Python.

**Two directions, both domain-neutral:**
1. **Take the inputs from the project itself**, for example
   `run_pipeline(path, inputs_from="leo_multicast.baseline:inputs", inputs_args=["space_kepler_offloading"])`,
   evaluated in the project's interpreter (R4's worker). This removes hand-copied JSON entirely,
   and is also what the R3 sweep driver will need: points built by the project's own code.
2. **At the JSON boundary only**, coerce an `int` to `float` where every consumer is annotated
   `float`, and **say so** in the response (for example `inputs_used.coerced`). The strict rule
   stays unchanged for Python callers.

## Small items

- **F-010:** `analyze_pipeline` lacks the `project=` / `python=` arguments that `validate`,
  `render`, `explain` and `run` gained in 1.26.
- **F-012:** on the end-to-end XDSM, the four group bands are contiguous but ordered
  constellation, ground, downlink, routing, not in registration order. `group_notes` is absent
  rather than an empty list.
- **F-013:** `explain` says "15 of 50 connections unit-checked" but not *which* 35 are not. A list
  would show where declaring units would help next.
- **F-014:** every `run_pipeline` stderr starts with a `RuntimeWarning` that
  `smartmdao.mcp._runner` was found in `sys.modules` before execution, which hides real warnings.

## Additions (later the same day)

**F-016 / F-017, the same boundary for structured inputs.** Some entry files take arrays, lists
of arrays, tuples and float-keyed dicts (satellite positions, ISL edge lists, bounding boxes). None
of these survive the trip through JSON unchanged: a tuple arrives as a list and is refused by its
annotation. **`inputs_from` (direction 1 above) would solve F-011, F-016 and F-017 at once**, since
the inputs would be built by the project's own code in the project's interpreter.

**F-018:** support `typing.Literal[...]` for option inputs (25 switchable decisions).
**F-019:** run only the steps that a requested output needs.

## The R3 cost note

Measured by hand, since no smoke run could pass the MCP. One core, with other runs in parallel, so
about ±30 %.

| What | Unit | Cost |
|---|---|---|
| Constellation + ISL | one pass, 100 realizations and 100 DL slots | Kepler 0.02–0.05 s; Starlink 0.13–0.17 s; worst stressed case 11.8 s |
| Routing | one realization (T_kg = 1..15 × 5 groups × 3 methods) | Kepler 64–86 ms; Starlink about 1.1 s (85 % Steiner) |
| Routing campaign | 100 realizations × 2 constellations × 2 scenarios | about 4 min serial |
| DL allocation | one slot (797 cells, about 6000 covered pairs) | P_DA 0.5–2.4 s (the solver dominates); P_fair 0.16–0.8 s; SCA alternative about 4 s |
| DL run | 100 slots | 70–260 s |
| Fig. 9 sweep | 74 runs | about 4–5 h serial |
| Stress plan | 45 entries | each multiplies one of the above |

**What a sweep driver needs**, from what had to be written by hand:
- points built by the project's own code (`baseline.inputs(scenario)` plus overrides), never
  hand-copied JSON;
- parallelism over realizations and slots, which are independent;
- a resumable store per point;
- seeds as inputs;
- per-point failure records: CLARABEL occasionally mis-reports infeasibility, and SCA can return
  "inaccurate";
- a cost quote from one point before the full run.
