# SmartMDAO 1.28.0 – 1.29.0: the answer to F-010 … F-019

Thanks for the second brief, and for the cost note. Everything in it is addressed below, in two
tagged releases. One item did not reproduce (F-010), and we need your help with it.

**To upgrade:** pin `smartmdao>=1.29.0` in your project's `.venv`, update the MCP server, and start
a new session. That last step matters for F-010.

## The blocker — F-011, and the same boundary for structured inputs (1.28.0)

**Whole numbers now work over MCP.** In `run_pipeline` and `compare_runs`, an integer is passed as
a float when every step reading it declares `float`. `inputs_used.coerced` names each one. It is
never done for a `bool`, never when some step reading the value declares nothing, and a number too
large to convert exactly (beyond 2^53) is refused rather than rounded. Python callers keep the
strict rule.

**Structured inputs come from your project, as you proposed:**

```
run_pipeline(path, inputs_from="leo_multicast.baseline:inputs",
             inputs_args=["space_kepler_offloading"], inputs_kwargs={...})
```

The function is called **inside the run process**, in your project's environment and under the
run's wall clock, so arrays, lists of arrays, tuples and float-keyed dicts never become JSON (F-016,
F-017). Precedence: anything you pass in `inputs`, then what the function builds, then the literals
in the file's own `run()` call. `inputs_used.built_by_project` lists what it built. The module is
found on the same path as the entry file's own imports, and `compare_runs` accepts the same
arguments. The analysis tools never call it, because they do not execute project code.

**One case to avoid:** a `Dict[float, float]` sent through JSON arrives with *string* keys, and it
passes the type check silently, because containers are checked on their outer type only. Build
such values with `inputs_from`.

## Small items

| Item | Release | What changed |
|---|---|---|
| **F-018** `Literal` | 1.28.0 | It was worse than a missing feature: a `Literal` annotation made `run()` crash for **every** value, valid ones included. Fixed. A value must be one of the options, the error names them, and a producer's options must fit the consumer's. A `Protocol` not marked `@runtime_checkable` crashed the same way; it is now unchecked. |
| **F-014** runpy warning | 1.28.0 | Gone from every run's stderr. |
| **F-012** group order | 1.29.0 | Groups ready at the same time follow the order they were written in. `group_notes` is always a list. |
| **F-013** unit coverage | 1.29.0 | `explain` lists the unchecked connections and which end lacks a unit (`g -> h (c; producer)`). `analyze_pipeline` returns the same as `unit_coverage`. |
| **F-019** only what an output needs | 1.29.0 | `pipeline.upstream("alloc")` returns a pipeline holding only the steps `alloc` depends on, with loops kept whole. Over MCP: `run_pipeline(targets=["alloc"])`. |

**F-010 did not reproduce.** A live 1.27.0 session advertises `python` and `project` on
`analyze_pipeline`, as on the other four tools, and a test now pins that on every release. The
likeliest cause is a client still holding the tool list from a session started on an older server.
If it happens again after a restart, please send the exact call and the error.
