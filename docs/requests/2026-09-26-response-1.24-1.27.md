# SmartMDAO 1.24.0 – 1.27.0: what changed for paper-repro

Thanks for the brief. Six of your seven requests have shipped, in four tagged releases, all on
PyPI. The last one, the sweep, waits on your first real runs.

**To upgrade:** pin `smartmdao>=1.27.0` in your project's `.venv` (1.26.0 is the minimum for R4), and update the MCP server (pull
`main` if you run it from a checkout with `uv run --directory`; otherwise
`pip install -U "smartmdao[mcp]"`), then start a new session.

## What you asked for, and where it is

| Request | Release | What to do |
|---|---|---|
| **R1** declared inputs (F-001, F-007) | 1.24.0 | `Pipeline(inputs=[...])` once in each entry file. analyze / validate / explain / render use it when a call passes no `inputs`; a list you do pass still wins. `inputs_used.declared` shows it was used. Your 91 names can go into the files instead of into 18 calls. |
| **R2** stubs (F-008) | 1.24.0 | Nothing: a step whose body is only `raise NotImplementedError` is reported. `analyze_pipeline` returns `stubs`, `explain` says "Not written yet (N of M steps)", and `validate` adds a `stub-step` **info** finding. A stubbed pipeline stays `valid`. |
| **R5** package-relative imports (F-005) | 1.24.0 | Entry files can live inside a package and use `from .physics import ...`. |
| **R6** grouped XDSM (F-002, F-006) | 1.25.0 | `@pipeline.step(outputs=[...], group="space")`. A group's steps stay together, in the run and on the diagram, with a band behind each group. Where dependencies make that impossible, `render_pipeline_diagram` returns `group_notes` naming the edges. |
| **R4** one server, many environments (F-009) | 1.26.0 | Nothing, once your `.venv` has 1.26.0: each file is handled in the nearest folder with a `pyproject.toml` and a `.venv`, so networkx / cvxpy / your GeoTIFF reader can be imported at the top of the file again. Every response says which environment was used, in `interpreter`. `python=` or `project=` choose one explicitly. |
| **R7** units (F-004) | 1.27.0 | `dB = Annotated[float, Unit("dB")]` on parameters and return values (dataclass fields and tuple elements work too). `validate` reports a `unit-mismatch` **error** where the two ends of a connection disagree, or where two steps read one input in different units. **Consistency checking only: nothing is ever converted.** An undeclared end is unchecked, and `explain` says how many connections were checked. The diagram shows units. Your `_db` / `_dbm` / `_mbps` names can become declarations. |

## Things you will notice

- **`interpreter` in every response.** If your `.venv` pins SmartMDAO older than 1.26.0, your
  files are still handled, in the server's environment as before, and `interpreter.note` asks you
  to upgrade. Nothing breaks on the day the server is upgraded.
- **New findings.** `unit-mismatch` (error) once you declare units. `unconsumed-input` (warning)
  flags a declared or passed input that no step reads, which is usually a typo. `type-mismatch` now
  also fires when two steps declare incompatible types for one input, which used to fail only at
  `run()`. `stub-step` and `groups-interleaved` are information only.
- **`run_pipeline` on a contract** runs the steps already written and stops at the first stub. The
  result lists `stubs` and, under `inputs_used.declared_not_supplied`, any declared input you did
  not pass.
- **Three bugs fixed that may have bitten you.** A `print()` in a discipline used to make
  `run_pipeline` fail with "not valid JSON". A file that printed while being analysed wrote into
  the MCP protocol stream. And after editing a sibling module (a discipline in `physics.py`), the
  server kept analysing the old version until it restarted. All three are fixed in 1.24.0–1.26.0.

## Still open

- **R3 sweep / Monte Carlo.** Designed to sit on the same worker as R4: seeds as inputs, a smoke
  run quoting the campaign's cost first, parallel isolated points, a resumable store, failures
  recorded. We are deliberately waiting for **your first real runs** before fixing its shape. A
  note on what the first campaign actually needed (points, run time, what failed, what you had to
  write by hand) would settle it.
- **`compare_runs`** still runs in the server's environment. It moves onto the worker together
  with the sweep.
